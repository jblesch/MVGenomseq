# Changelog
## [2.0.0] - 2026-09-01

The changes below were checked against an aggregated survey of the submission databases of all six GRZs: 15,721 submissions carrying metadata, holding 25,168 `labData` entries. Values were removed only where the survey showed them unused, and controlled vocabularies were extended where submissions in service had no correct value to give. Figures quoted in the entries come from that survey.

Two things to keep in mind when reading them. Counts such as 25,168 are per `labData` entry rather than per submission, since a submission may carry several. And absence of a value is evidence for removing it only where the value is not held open for a process yet to start: `submissionType: followup` and `sequenceType: rna` are unused today and were left untouched for that reason.

Survey tool used: https://github.com/jblesch/grz_query_metadata

### Added
  - Added `$id` identifying the schema by its release tag, making it referenceable via `$ref`.
  - Added optional `submission.schemaVersion` so a submission declares which schema version it conforms to.
  - **BREAKING**: Added required `donors[].labData[].caseControlStatus`, so that the case/control role of each sample is stated explicitly instead of being inferred from `diseaseType`, `relation` and `sequenceSubtype`. Those fields cannot express the distinction reliably: `relation` can misclassify affected relatives — an affected parent in a dominant condition derives to 'control' — and in hereditary cancer the same germline sample is the case sample where the predisposing variant lies, but the matched normal in a sporadic tumour, so `relation` and `sequenceSubtype` together give opposite answers for identical field values. `unknown` is deliberately not offered: Leistungserbringer know the status of the samples they submit, so the value would only serve as an escape hatch that is not needed.
  - Added `aunt`, `uncle`, `grandparent` and `grandchild` to `donors[].relation`, to accommodate more complex pedigrees. Existing values are unchanged and `other` is retained. 
  - Added optional `donors[].labData[].readStructure`, describing where the UMI and barcode segments sit within the sequencing reads (`readType`, 0-based `offset`, `length`, `segmentType`). The layout is a property of the library design, so it is recorded once per lab dataset rather than repeated per file. Required for deduplication and consensus calling when research-consented submissions are reanalysed.
  - Added `donors[].labData[].umiKitName`, `umiKitManufacturer` and `customUmiUsed`, required whenever `readStructure` declares a `umi` segment and absent otherwise.
### Changed
  - **BREAKING**: `sampleConservation`, `fragmentationMethod`, `libraryType`, `enrichmentKitManufacturer`, `sequencerManufacturer`, `libraryPrepKitManufacturer`, `libraryPrepKit`, `sequencerModel`, `tissueOntology.name`, `relation`, `sequencingLayout` and `tumorCellCount[].method` each gained a companion field named after it with the suffix `Other` (`sampleConservationOther`, `relationOther`, and so on) that is required and must be non-empty when the value is `other`. `donors[].gender` is the sole deliberate exception: `other` there is a valid self-description rather than a missing value. The entries collected there are intended to be reviewed periodically, so that recurring values can be promoted into the enums and uninformative ones followed up with the submitting Leistungserbringer. `unknown` is unaffected.
  - **BREAKING**: `donors[].labData[].sequencerManufacturer` is no longer required, and where it is given it must be one of nine controlled values. Once `sequencerModel` is controlled the manufacturer follows from the model for all but `other` and `unspecified`, so the field carries no information the submission does not already hold. Leaving it free text was the worse option: the survey found five companies recorded under twelve spellings — `Illumina`, `Illumina Inc.` and `illumina`; `ONT` and `Oxford Nanopore Technologies` — so no consumer could group by manufacturer without normalising first. Where the manufacturer is not listed, `other` requires the new `sequencerManufacturerOther`. Submissions that omit the field now validate; those that keep sending the old spellings do not.
  - **BREAKING**: `donors[].labData[].kitManufacturer` is now controlled, using the same list of manufacturers as `libraryPrepKitManufacturer` and `enrichmentKitManufacturer`. Free text had produced 27 spellings for seven companies, and the survey shows the field is not merely untidy but wrong in places: 319 entries are empty, 77 carry a stray concatenation (`Illumina+`, `Illumina+Illumina`, `+`, `++`), and 31 are misspelled (`Illuminia`, `Pacific Bioscience`). None of the 427 affected entries names a manufacturer the list lacks, so adopting it rejects defects rather than legitimate values. Where the manufacturer is not listed, `other` requires the new `kitManufacturerOther`. `kitName` remains free text: like `libraryPrepKit` it mixes products that no single vocabulary covers, in this case flow cells (`10B`, `S4`) and sequencing reagent kits (`NovaSeq 6000 S4 Reagent Kit v1.5`).
  - **BREAKING**: Values never used in any submission were removed: `unknown` from `fragmentationMethod`, and `other` and `unknown` from `sequenceSubtype`. None occurs in the 25,168 entries surveyed, and each described an absence of information rather than a fact about the sample — a laboratory knows how it fragmented the material and whether it sequenced germline or somatic DNA. `sequenceSubtype` is therefore closed to `germline` and `somatic`, which between them account for every entry in service. `tumorCellCount[].method` is left untouched: `unknown` is used 698 times, because a count supplied by an external pathology report may genuinely arrive without its provenance, and `other` is retained although unused, since a third way of establishing a tumour cell count is possible and its absence to date is not evidence that none exists. The companion field `sequenceSubtypeOther` is removed with the value that required it.
  - **BREAKING**: `donors[].labData[].enrichmentKitDescription` is required only when `enrichmentKitManufacturer` names a manufacturer, and must be non-empty where it is given. It was previously required of every entry, including the majority that performed no enrichment at all, and the survey shows what that produced: 16,312 entries — 64.8% of the field — say nothing, in nine different ways (`none`, `''`, `no_enrichment_kit_used`, `n.a.`, `na`, `n/a`, `NA`, `unknown`, `none `). Recording the same absence twice also let the two fields disagree, which they do in 1,182 entries. The absence of enrichment is now stated once, by `enrichmentKitManufacturer: none`. An enum was considered for the kit name and rejected for the same reasons as `libraryPrepKit`: the 8,856 entries that do name a kit include custom capture designs that appear in no vendor catalogue (`Twist Custom Exome IMGAG V2 Covaris`), all-in-one products that legitimately appear in both fields (`Illumina DNA Prep with Enrichment`), and free-form typos in service (`Twist Hybridization Reagnet`, 955 entries).
  - **BREAKING**: `donors[].labData[].enrichmentKitManufacturer` now uses the same list of manufacturers as `libraryPrepKitManufacturer`, lower-cased. It previously offered four companies, which forced 1,715 entries (6.8%) onto `other` — IDT in particular supplies enrichment panels in service at several sites and had no value of its own. Values were also capitalised, making it the only enum in the schema mixing cases; since enum matching is case-sensitive, a submitter following the schema's otherwise uniform lowercase convention would have been rejected without being told why. `unknown` is dropped, used three times in 25,168 entries and describing an absence of information rather than a fact; `none`, which records that no enrichment was performed and accounts for 60% of entries, is unaffected.
  - **BREAKING**: `donors[].labData[].sampleConservation` is adapted; `cryo-frozen` is replaced by `freezer`, `ultra-low-freezer` and `cryogenic-freezer`, so that storage temperature is recorded rather than lost; `refrigerator` and `none` are new. `fresh-tissue` is retained. Submissions using `cryo-frozen` no longer validate.
  - **BREAKING**: `donors[].labData[].sequencerModel` is now controlled, adopting the `instrument_model` vocabulary of the GHGA ExperimentMethod entity (70 values). Where `other` is used, the new `sequencerModelOther` must name the model. Free-text values no longer validate. Three current-generation instruments absent from the source vocabulary were added: `illumina_novaseq_x_plus`, `nextseq_550dx` and `revio`. The first matters most — 11,395 entries (45%) were recorded on a NovaSeq X Plus, which the source vocabulary cannot name, leaving those sites a choice between `other` and claiming a NovaSeq X they do not own.
  - **BREAKING**: `donors[].labData[].libraryPrepKit` stays free text and is not controlled, while `libraryPrepKitManufacturer` becomes a controlled list of fourteen values. A controlled kit list was abandoned: the survey found 93 distinct kit names, of which the candidate vocabulary covered 8%, and the shortfall is not a spelling problem. Sites record bare vendor names (`Twist`, 955 entries) that identify no particular kit, internal designations (`GenomV2`, 1,407), and custom capture designs (`Twist Custom Exome IMGAG V2 Covaris`) that exist in no vendor catalogue. Library preparation kits are also released continuously, so any closed list is out of date on publication. The manufacturer, by contrast, is a short and stable list: the survey found twelve companies written twenty-five ways, `Twist` alone appearing five times over. Controlling the manufacturer therefore yields a queryable axis without discarding what laboratories actually record, and the kit name remains available in full. Where the manufacturer is not listed, `other` requires the new `libraryPrepKitManufacturerOther`; `none` covers submissions prepared without a kit. All but two of 25,168 entries map onto the new list.
  - **BREAKING**: The vocabulary above lives in a separate file under `GRZ/vocabularies/` and is pulled into the schema with `$ref`, to keep `grz-schema.json` itself readable. Validators must be given the vocabulary file as well as the schema. 
  - **BREAKING**: `donors[].labData[].libraryType` is kept as a single field, with three values removed. `wxs` and `wxs_lr` name the same thing as `wes` and `wes_lr`, so offering both let two submitters describe an identical experiment differently with nothing to catch it. Which spelling to retire was settled by measurement rather than preference: `wes` occurs 6,213 times and `wxs` not once, so retiring `wxs` invalidates no submission observed to date while retiring `wes` would have required every exome submission in service to be rewritten. `unknown` is removed on the same evidence — never used, and a laboratory always knows the library it prepared, so the value recorded an absence of information rather than a fact about the sample. A library type outside the list is expressed as `other`, which now requires the new `libraryTypeOther` to name it. 
  - **BREAKING**: Removed `reverse` from `donors[].labData[].sequencingLayout`. The field states how many reads were produced per fragment, one or two, whereas `reverse` describes which direction a read represents — an orthogonal property. A run recorded as `reverse` is in fact single-end, so the value left a consumer unable to tell how many read files to expect. The survey settles the practical question: `reverse` was used in none of the 25,168 lab-data entries, at any of the six GRZs, while `paired-end` accounts for 24,617 (97.8%), `single-end` for 487 (1.9%) and `other` for 64 (0.3%). Removing it therefore invalidates no submission observed to date. Read direction is carried where it belongs: which read a file holds is given by `sequenceData.files[].readOrder`, and the internal composition of the reads by `readStructure`.
  - Added per-value explanations to the descriptions of `sequencingLayout` and `libraryType`. The previous `libraryType` description was just "Library type", which left every value unexplained.
  - Added `I1` and `I2` to `donors[].labData[].sequenceData.files[].readOrder`, so that submitted index-read files can be identified; previously only `R1` and `R2` were expressible.
  - Clarified that `donors[].labData[].barcode` holds the barcode sequence itself, its position being described by `readStructure`.
  - **BREAKING**: `donors[].labData[].tissueOntology.name` is now a controlled value — `bto`, `uberon`, `snomed_ct` or `other` — and `tissueTypeId` must match the identifier format of whichever is named: `^BTO[:_][0-9]{7}$`, `^UBERON[:_][0-9]{7}$`, or a plain SNOMED CT concept number. Both the CURIE form `BTO:0000089` and the OBO form `BTO_0000089` are accepted; `nameOther` names any tissue ontology outside the list.

    The field was previously unconstrained, and the survey found 42 spellings in it — BRENDA alone written ten ways — so an identifier could not be attributed to a vocabulary, and an identifier means nothing until one knows which ontology issued it. Mandating a single ontology was considered and rejected: BRENDA is the most used at 31.6% of entries but still a minority, and requiring it would have invalidated the majority of submissions in service.

    Classifications of disease are excluded deliberately. `tissueTypeId` records which tissue a sample was taken from — nothing else. ICD-O and OncoTree codes account for 32% of entries today and are simply the wrong kind of value here: they state what a tumour is, which is a diagnosis, not an anatomical site. Leaving them in means no consumer can tell whether `tissueTypeId` holds a body part or a morphology code, which defeats the point of recording the tissue at all. Sites entering a diagnosis here must carry it in the clinical dataset instead; `bto`, `uberon` and `snomed_ct` all name anatomical structures, and a disease classification does not become a tissue ontology by being declared as `other`.
  - **BREAKING**: if BAM or FASTQ files are submitted for a donor, at least one VCF file must be submitted for that same donor, so that research-consented submissions can be reanalysed without reprocessing the raw sequence data. The requirement is counted per donor deliberately: it makes every VCF unambiguously attributable to a donor, which a per-submission rule cannot do, since the schema cannot inspect which sample columns a jointly genotyped VCF contains. Where variants are called jointly across a trio, the resulting VCF must therefore be listed under each donor it covers; the same file may be declared more than once. A tumor/normal pair belongs to a single donor, so its joint VCF is provided once. The rule applies to every library type and every `submissionType`, so raw reads cannot be delivered ahead of variant calls, and a library declared as `other` is not exempt. Submissions with no BAM or FASTQ files, and empty `files` lists, remain valid as before.
